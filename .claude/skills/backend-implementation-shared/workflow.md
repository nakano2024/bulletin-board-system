# バックエンド実装の共通手順

`backend-implementation-domain` / `backend-implementation-usecase` / `backend-implementation-infra` / `backend-implementation-handler` / `backend-implementation-integration` の各スキルが共通で従う手順。各スキルは、層ごとの対象と手順だけを持ち、それ以外はこのファイルに従う。

このスキル群は、**1つの API エンドポイントを実装すること**を前提に進める。API 以外の単位(バッチ処理、CLI など)の依頼には使わない。

## 層の順序

1つの API の実装は、次の5つのスキルをこの順に使って進める。**層を飛ばしたり、順序を入れ替えたりしない。**

| 順番 | スキル | 対象 |
| --- | --- | --- |
| 1 | `backend-implementation-domain` | Entity / Aggregate、DomainService、`IRepository` インターフェース、センチネルエラー |
| 2 | `backend-implementation-usecase` | `XxUsecase`、DTO(`XxCommand` / `XxOutput`)、`IQueryService` など application 層の汎用インターフェース |
| 3 | `backend-implementation-infra` | `IRepository` / `IQueryService` / 汎用インフラの実装 |
| 4 | `backend-implementation-handler` | ハンドラ、リクエスト / レスポンス型、エラー変換 |
| 5 | `backend-implementation-integration` | `main.go` での DI 配線・ルーティング登録、E2E テスト |

前の層がユーザー確認まで完了していない状態で、次の層のスケルトン実装に着手しない。各層は、前の層で確定したインターフェース・型の実物を前提に組み立てる。

## 実装対象の確認

作業を始める前に、実装対象の API を確定させる。

- 同じ会話の中で、前の層のスキルですでに実装対象が確定している場合は、それを引き継ぐ。引き継ぐ旨(例: 「`POST /threads` の Usecase 層に進みます」)をユーザーに一言伝える。
- 確定していない場合は、ユーザーに「どの API を実装するか」を自由入力で尋ねる。選択式にせず、`.claude/rules/backend-architecture.md` の「プレゼンテーション層(ハンドラ)」のルーティング表に沿う形(メソッド + パス、例: `POST /threads`)で具体的に答えてもらう。
- ユーザーが実装対象の API を答えるまで、スケルトン実装を含め一切のコードを書き始めない。
- **実装範囲は、ユーザーが指定した1つの API エンドポイントに厳密に限定する。** CLAUDE.md などの仕様書に他の API や機能の記載があっても、指定されていない範囲は実装しない。
- 作業中に「ついでにこれも直したほうがいい/実装したほうがいい」と気づいても、勝手に実装しない。気づいた点はユーザーへの提案として伝えるだけに留め、指示があるまで手を付けない。

## 前提の確認

各スキルは、着手前に「前の層が完了しているか」をコードで確認する(各スキルの「前提」節を参照)。前の層の型・インターフェースが存在しない、または今回の API に必要な形になっていない場合は、自分の層で補わずにユーザーへ伝え、前の層のスキルに戻るかどうかを確認する。

## 各層の4フェーズ

各層の中では、次の4フェーズをこの順番で進める。**フェーズを飛ばしたり、順序を入れ替えたりしない。**(フェーズの具体的な中身は層ごとのスキルに書かれている。`backend-implementation-integration` だけはフェーズの中身が異なる)

1. スケルトン実装
2. テストケースの洗い出し
3. テストコードの実装
4. 本実装

各フェーズは「実装 → サブエージェントによる判定 → ユーザー確認」の3ステップで構成される。判定が OK になり、かつユーザーが OK を選ぶまで、次のフェーズにも次の層にも進まない。

### フェーズ共通の約束

- スケルトン実装では、メソッドの中身は `panic("not implemented")` で置く。
- テストケースの洗い出しでは **コードは書かない。** `.claude/rules/backend-testing.md` の「テストケースの定義」に従い、「XXであること」の形式で列挙する。境界値と代表値が必要な箇所は必ず両方洗い出す。
- テストコードの実装では、前フェーズで承認されたケース一覧をそのままテストコードに落とす。ケースを勝手に増減しない。増減したくなったらユーザーに相談する。
- 本実装では、テストが通るように中身を実装する。**フェーズ3のテストは変更しない。**
- gomock のモックが必要になった場合は、既存のモック(`mockgen` のヘッダコメント)に倣い、そのテストを書くフェーズで生成する。

## 常に守ること

この手順は複数ターンにまたがる。スキルの内容は一度読み込まれた後、後続のターンで再読み込みされないので、以下は会話が続く間ずっと有効な指示として扱う。

- 各ターンの冒頭で、いま「どの層」の「どのフェーズ」にいるかを確認してから作業する。ユーザーの確認待ちで中断していた場合は、承認された地点の次のステップから再開する。
- ユーザーへの確認は必ず親(この会話)で行う。サブエージェントはユーザーに質問できないため、判断が必要なことをサブエージェントに委ねない。
- 実装範囲は「実装対象の確認」で決めた1つの API エンドポイントに限定する。範囲を広げたくなったら、実装せずユーザーに相談する。
- **現在の層のファイルだけを変更する。** 現在の層の変更によって、他の層の既存コード(すでに実装済みの別 API の Usecase / Infra / Handler / `main.go` など)がコンパイルできなくなっても、`go build ./...` を通すために他の層を勝手に直さない。小さな機械的修正(スタブメソッドの追加、コンストラクタ引数の追加など)であっても同じ。現在の層の作業はそこで止め、どのファイル・どの層に対応する変更が必要になるか(どの層のスキルで扱うか)をユーザーに伝え、進め方を確認する。
- 1つの層が完了したら、次の層のスキルに自動で進まない。完了をユーザーに伝え、次に使うスキル名を案内する。

## 参照するルール

作業を始める前に必ず両方を読む。

- `.claude/rules/backend-architecture.md` — 設計ルール
- `.claude/rules/backend-testing.md` — テストルール

## 判定ループの共通手順

各フェーズで使うサブエージェントは異なるが、ループの回し方は共通。

1. 実装(または一覧の作成)を行う。対象は現在の層に閉じる。
2. 対象ファイルのパスを明示して、担当のサブエージェントに判定を依頼する。
3. 返ってきた JSON を読む。
   - `verdict: OK` → ユーザー確認に進む。
   - `verdict: NG` → 各 `violation` の `suggested_fix` に従って直し、再度 2 に戻る。
   - `verdict: unclear` → 判定できなかった理由をユーザーに伝え、指示を仰ぐ。自己判断で先に進まない。
4. **NG が3回続いたら、ループを打ち切ってユーザーに相談する。** 同じ指摘が繰り返される場合、コードではなくルールの側が曖昧である可能性が高い。どの指摘で詰まっているかを示して判断を仰ぐ。

サブエージェントは呼び出すたびに新しいインスタンスになり、この会話の履歴も前回の判定内容も引き継がない。再判定のたびに、対象ファイルのパスと参照すべきルールファイルのパスを渡し直す。「さっきの指摘を直したので再確認して」だけでは、相手には何も伝わらない。

指摘に納得できない場合も、勝手に無視しない。ユーザーに「この指摘は誤検知だと思う」と根拠を添えて相談する。誤検知が確認できたら、ルールファイルの記述を直す提案までセットで行う。

## ユーザー確認の出し方

各フェーズの最後に、AskUserQuestion で確認を取る。確認を求める前に、そのフェーズで作ったものの要点(ファイル一覧、主要な判断、サブエージェントが指摘して直した点)を3〜5行でまとめて提示する。

選択肢は「OK、次に進む」「修正したい点がある」の2つを基本とする。

## 判定の信頼性を上げたいとき

サブエージェントの判定は確率的なので、同じコードでも結果が揺れる。重要な判定(各層のフェーズ1とフェーズ4の architecture-reviewer)でブレが気になる場合は、同じ依頼を3体並列で投げ、2体以上が同じ違反を指摘したものだけを採用する。

コストは3倍になるが、誤検知による修正の空回りは減る。通常は単発で回し、判定が安定しないと感じたときだけ使う。
