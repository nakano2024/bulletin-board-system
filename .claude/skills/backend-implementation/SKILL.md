# バックエンド実装

このスキルは、**1つの API エンドポイントを実装すること**を前提に進める。API 以外の単位(バッチ処理、CLI など)の依頼には使わない。

## 実装対象の確認

作業を始める前に、会話の中でユーザーに「どの API を実装するか」を自由入力で尋ねる。選択式にせず、`.claude/rules/backend-architecture.md` の「プレゼンテーション層(ハンドラ)」のルーティング表に沿う形(メソッド + パス、例: `POST /threads`)で具体的に答えてもらう。

- ユーザーが実装対象の API を答えるまで、スケルトン実装を含め一切のコードを書き始めない。
- **実装範囲は、ユーザーが指定した1つの API エンドポイントに厳密に限定する。** CLAUDE.md などの仕様書に他の API や機能の記載があっても、指定されていない範囲は実装しない。
- 作業中に「ついでにこれも直したほうがいい/実装したほうがいい」と気づいても、勝手に実装しない。気づいた点はユーザーへの提案として伝えるだけに留め、指示があるまで手を付けない。

## 実装の大枠順序

1つの API の実装は、次の3グループの順に進める。**グループを飛ばしたり、順序を入れ替えたりしない。**

1. **Domain層** — Entity / Aggregate、DomainService、`IRepository` インターフェース
2. **Usecase層** — `XxUsecase`、DTO（`XxCommand` / `XxOutput`）、`IQueryService` など application 層の汎用インターフェース
3. **Infra層・Handler層** — `IRepository` / `IQueryService` などの実装、ハンドラ、`main.go` での DI 配線

前のグループがユーザー確認まで完了していない状態で、次のグループのスケルトン実装に着手しない。Usecase層は Domain層の実物（Entity・Aggregate・IRepository インターフェース）を前提に組み立て、Infra層・Handler層は Usecase層が確定したインターフェースを前提に実装する。

各グループの中では、次の4フェーズをこの順番で進める。**フェーズを飛ばしたり、順序を入れ替えたりしない。**

1. スケルトン実装
2. テストケースの洗い出し
3. テストコードの実装
4. 本実装

つまり全体としては「3グループ × 4フェーズ」を順番に進めることになる。各フェーズは「実装 → サブエージェントによる判定 → ユーザー確認」の3ステップで構成される。判定が OK になり、かつユーザーが OK を選ぶまで、次のフェーズにもグループにも進まない。

## 常に守ること

この手順は複数ターンにまたがる。スキルの内容は一度読み込まれた後、後続のターンで再読み込みされないので、以下は会話が続く間ずっと有効な指示として扱う。

- 各ターンの冒頭で、いま「どのグループ」の「どのフェーズ」にいるかを確認してから作業する。ユーザーの確認待ちで中断していた場合は、承認された地点の次のステップから再開する。
- ユーザーへの確認は必ず親（この会話）で行う。サブエージェントはユーザーに質問できないため、判断が必要なことをサブエージェントに委ねない。
- 実装範囲は「実装対象の確認」で決めた1つの API エンドポイントに限定する。範囲を広げたくなったら、実装せずユーザーに相談する。

## 参照するルール

作業を始める前に必ず両方を読む。

- `.claude/rules/backend-architecture.md` — 設計ルール
- `.claude/rules/backend-testing.md` — テストルール

## 判定ループの共通手順

各フェーズで使うサブエージェントは異なるが、ループの回し方は共通。

1. 実装(または一覧の作成)を行う。対象は現在のグループの層に閉じる。
2. 対象ファイルのパスを明示して、担当のサブエージェントに判定を依頼する。
3. 返ってきた JSON を読む。
   - `verdict: OK` → ユーザー確認に進む。
   - `verdict: NG` → 各 `violation` の `suggested_fix` に従って直し、再度 2 に戻る。
   - `verdict: unclear` → 判定できなかった理由をユーザーに伝え、指示を仰ぐ。自己判断で先に進まない。
4. **NG が3回続いたら、ループを打ち切ってユーザーに相談する。** 同じ指摘が繰り返される場合、コードではなくルールの側が曖昧である可能性が高い。どの指摘で詰まっているかを示して判断を仰ぐ。

サブエージェントは呼び出すたびに新しいインスタンスになり、この会話の履歴も前回の判定内容も引き継がない。再判定のたびに、対象ファイルのパスと参照すべきルールファイルのパスを渡し直す。「さっきの指摘を直したので再確認して」だけでは、相手には何も伝わらない。

指摘に納得できない場合も、勝手に無視しない。ユーザーに「この指摘は誤検知だと思う」と根拠を添えて相談する。誤検知が確認できたら、ルールファイルの記述を直す提案までセットで行う。

## ユーザー確認の出し方

各フェーズの最後に、AskUserQuestion で確認を取る。確認を求める前に、そのフェーズで作ったものの要点(ファイル一覧、主要な判断、サブエージェントが指摘して直した点)を3〜5行でまとめて提示する。

選択肢は「OK、次に進む」「修正したい点がある」の2つを基本とする。

## グループ1: Domain層

対象: Entity / Aggregate、DomainService、`IRepository` インターフェース(`domain/`)。Usecase型・DTO・Handler など他層のコードはこのグループでは作らない。

### フェーズ1: スケルトン実装

作るもの:

- ドメインモデル(Entity / Aggregate)の型とコンストラクタのシグネチャ
- DomainService の型とメソッドシグネチャ(必要な場合のみ)
- `IRepository` インターフェース

メソッドの中身は `panic("not implemented")` で置く。判定は **architecture-reviewer** に依頼する。

ユーザー確認では、集約の切り方と `IRepository` のメソッドの切り方(業務単位で閉じているか)を重点的に見てもらう。

### フェーズ2: テストケースの洗い出し

**コードは書かない。** CLAUDE.md の仕様のうち、ドメインモデル・DomainService の振る舞いに関わるケースを洗い出す。Usecase の入出力バリデーションなど Usecase層の責務にあたるケースは、ここでは含めない(グループ2で洗い出す)。

`.claude/rules/backend-testing.md` の「テストケースの定義」に従い、「XXであること」の形式で列挙する。境界値と代表値は必ず両方洗い出す。

判定は **testcase-reviewer** に依頼する。

### フェーズ3: テストコードの実装

フェーズ2で承認されたケース一覧を、そのままテストコードに落とす。`.claude/rules/backend-testing.md` の「共通ルール」「ドメインモデルのテスト」「ドメインサービスのテスト」に従う。

判定は **test-code-reviewer** に依頼する。

### フェーズ4: 本実装

テストが通るように中身を実装する。フェーズ3のテストは変更しない。

グループ完了時、**architecture-reviewer** に再度判定を依頼する。OK かつユーザー確認が取れたら、グループ2に進む。

## グループ2: Usecase層

対象: `XxUsecase`、DTO(`XxCommand` / `XxOutput`)、`IQueryService` など application 層の汎用インターフェース(`application/`)。`IRepository` の実装や Handler はこのグループでは作らない — グループ1で定義した `IRepository` インターフェースをそのまま使う。

### フェーズ1: スケルトン実装

作るもの:

- ユースケース型 `XxUsecase` と `Exec()` のシグネチャ
- DTO(`XxCommand` / `XxOutput`)
- `IQueryService`、`ITimeGetter`、`IUuidGenerator` など application 層の汎用インターフェース

判定は **architecture-reviewer** に依頼する。

ユーザー確認では、DTO にドメインモデル型が混ざっていないか、`Exec()` が「取得 → ドメインモデルに委譲 → 保存」の組み立てに徹する形になっているかを重点的に見てもらう。

### フェーズ2: テストケースの洗い出し

**コードは書かない。** `Exec()` の入力に対してどの出力・エラーを返すかを基準にケースを洗い出す。

判定は **testcase-reviewer** に依頼する。

### フェーズ3: テストコードの実装

`.claude/rules/backend-testing.md` の「ユースケースのテスト」に従う。`IRepository` / `IQueryService` / 汎用インフラは gomock でモックする(具象実装がまだ存在しなくても、インターフェースが確定していればモックできる)。ドメインモデル・DomainService はモックせず実物を使う。

この時点では Infra の実装がないため、`IRepository` 等の呼び出し以外の実装(main.go の DI 配線など)は不要。判定は **test-code-reviewer** に依頼する。

### フェーズ4: 本実装

テストが通るように中身を実装する。フェーズ3のテストは変更しない。

グループ完了時、**architecture-reviewer** に再度判定を依頼する。OK かつユーザー確認が取れたら、グループ3に進む。

## グループ3: Infra層・Handler層

対象: `IRepository` / `IQueryService` などの実装(`infra/`)、ハンドラ(`handler/`)、`main.go` での DI 配線。

### フェーズ1: スケルトン実装

作るもの:

- `infra/` の実装型のシグネチャ(`PostgresThreadRepository` など、技術要素を含む名前)
- ハンドラの型とメソッドシグネチャ。`.claude/rules/backend-architecture.md` の「プレゼンテーション層(ハンドラ)」(ルーティング・エラーのステータスコード方針)に従う
- `main.go` での DI 配線の骨子

判定は **architecture-reviewer** に依頼する。

### フェーズ2: テストケースの洗い出し

`.claude/rules/backend-testing.md` の「インフラのテスト」に従い、DB を伴う `infra/` のテストケースを洗い出す。ハンドラのテストについては本ルールセットに方針の定義がないため、洗い出し対象は `infra/` を中心とする。ハンドラのテストを書きたい場合はユーザーに方針を確認してから進める。

判定は **testcase-reviewer** に依頼する。

### フェーズ3: テストコードの実装

`.claude/rules/backend-testing.md` の「インフラのテスト」に従う。DB がある場合は「データを投入 → 検証 → データを壊す」のフローをトランザクションで実装する。

判定は **test-code-reviewer** に依頼する。

### フェーズ4: 本実装

テストが通るように中身を実装し、`main.go` で具象実装をコンストラクタ経由で注入する。フェーズ3のテストは変更しない。

全テストが通ったら、最後にもう一度 **architecture-reviewer** に、今回実装した API に関わる全ファイル(Domain / Usecase / Infra / Handler)を通しで判定依頼する。スケルトンや各グループ単体では見えなかった違反(インフラへのロジック混入、ドメイン層での `time.Now()` 呼び出しなど)が、実装後に初めて現れるため。

最後のユーザー確認をもって、実装対象の API は完了とする。

---

## 判定の信頼性を上げたいとき

サブエージェントの判定は確率的なので、同じコードでも結果が揺れる。重要な判定(各グループのフェーズ1とフェーズ4の architecture-reviewer)でブレが気になる場合は、同じ依頼を3体並列で投げ、2体以上が同じ違反を指摘したものだけを採用する。

コストは3倍になるが、誤検知による修正の空回りは減る。通常は単発で回し、判定が安定しないと感じたときだけ使う。
